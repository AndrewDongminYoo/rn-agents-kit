# Commands

Every command here is read-only with respect to the target project: none of them writes, installs, or executes code the project owns.
A discovered Plug'n'Play loader is reported as evidence, never preloaded, so no row can be affected by what that loader does.

## No row prints an original file's contents

A row here does one of three things: it returns paths and status, it prints what a file contains, or it hands a file to a bundled helper and prints what the helper returns.

A row of the second kind reads a redacted copy that the user has approved, named by a `REDACTED_` variable, and never the path discovery returned. A row of the third kind takes the original — `Read a discovered manifest`, `Read an npm lockfile`, `Read a pnpm lockfile`, `Read an eas config`, `Read a pnpm workspace catalog`, `Read an external Node pin`, `Read a Yarn linker` — because what it prints is bounded at the output rather than at the input. That list is stated here and nowhere else; `SKILL.md` points at it rather than repeating it. Do not ask for a copy for those rows, and do not delay or skip them for want of one.

The rule for the second kind is unconditional, and that is the point. An earlier design decided per file whether an original was safe to read, using patterns that looked for credential-shaped key names and printed what they judged safe. Deciding that correctly has no closed form: every narrowing dropped a value the assessment needed, every widening printed part of a secret, and the counterexamples did not run out — a private registry port pulled a token into a userinfo match, a package name spelled like a credential lost its version, an identity term that a secret happened to start with consumed the rest of it. Removing the decision removes the whole class.

So there is no credential scan row, and no row judges a file. What a redacted copy contains is the user's decision, made once per file, outside this skill.

The helpers bound their output instead, each in its own way.

`rn-upgrade-pulse.mjs` bounds it by projection. Every field it emits is a path, a token validated whole against a fixed character class, or a projection of named manifest fields — a value that does not validate makes the result `ambiguous` instead of being printed. `expo` and `scripts` project to key names only, because their contents have no shape the projection can bound. `SKILL.md` records under Not Examined what that leaves unread.

`evidence.mjs` bounds it by schema. Each file kind has an adapter with a fixed set of field names and a declared type for each, and a value reaches the output only when its type accepts it whole; a field the schema does not name is never read, and a value that does not validate is reported by field name with the value left behind. It emits no path and no key, and it reports a parse failure by code rather than by the parser's message. It reads the original for the kinds it claims, which is why its rows take a path from discovery rather than a `REDACTED_` copy.

## The Node rows cannot write into the target

Every Node row clears four environment variables, sets `NODE_DISABLE_COMPILE_CACHE`, and passes `--no-global-search-paths`.

`NODE_COMPILE_CACHE` and `NODE_V8_COVERAGE` each break the read-only promise outright: pointed beneath the target, the first makes Node write a cache directory and bytecode there while the helper starts, and the second makes it write a coverage file when the helper exits. Node resolves a relative `NODE_V8_COVERAGE` against the working directory, which no row pins.
`NODE_OPTIONS` carries `--require`, so a caller's value would preload that module into the helper, which for a project-owned file means this skill executes project code before it reads anything.
`NODE_PATH` prefixes directories onto the module search path, so a caller's value can satisfy a dependency the app has not installed, and a path inside the repository passes the outside-`REPO_DIR` check as well. `--no-global-search-paths` closes what clearing `NODE_PATH` leaves open, because `$HOME/.node_modules` still satisfies a resolution and passes that same check when `HOME` is the repository.

Set these before running a row:

- `REPO_DIR` — the repository root, `APP_DIR` — the selected app root.
- `SKILL_DIR` — the absolute base directory of this skill, so the bundled helper can be invoked.
- `MANIFEST_PATH` — each discovered manifest in turn, the app manifest included. This one is the original: it is read by the bundled helper, not by a row.
- `LOCKFILE_PATH` — each discovered `package-lock.json` or `npm-shrinkwrap.json` in turn. Also an original, read by `evidence.mjs`, which reports the locked version rather than proof of an install. Its row also passes `APP_DIR`, because a lockfile describing a workspace holds one answer per workspace and the app is what picks between them. A `yarn.lock` has an adapter too, for the generation that wrote it rather than for any version, and it is read by the install-mode walk inside `rn-upgrade-pulse.mjs` rather than by a row here. `bun.lock` and `bun.lockb` have no adapter and keep taking `REDACTED_LOCKFILE` for their versions.
- `PNPM_LOCKFILE_PATH` — each discovered `pnpm-lock.yaml` in turn. Also an original, read by `evidence.mjs`, which reports the lockfile version and the versions the selected importer resolved. Its row passes `APP_DIR` for the reason the npm one does: a pnpm lockfile always describes its importers separately, and the app is what picks between them.
- `EAS_CONFIG_PATH` — the discovered `eas.json`. Also an original, read by `evidence.mjs`. This one adds evidence rather than replacing a row: `REDACTED_EAS_CONFIG` is still what `Find generation and build declarations` reads.
- `NODE_PIN_PATH` — each discovered external Node pin in turn. Also an original, read by `evidence.mjs`, which reports the pinned Node version and nothing else from the file. This one replaces its row's copy rather than adding beside it: there is no `REDACTED_NODE_PIN`.
- `YARNRC_PATH` — the discovered `.yarnrc.yml`. Also an original, read by `evidence.mjs`, which reports the linker that file declares and nothing else from it. It gets a variable of its own rather than sharing `WORKSPACE_CONFIG_PATH` with `pnpm-workspace.yaml`, because two different files under one name is how a row ends up reading the wrong one.
- `WORKSPACE_CONFIG_PATH` — the discovered `pnpm-workspace.yaml`. Also an original, read by `evidence.mjs`, which reports the default catalog's `react`, `react-native` and `expo` ranges and nothing else from the file. This one also adds evidence rather than replacing a row: `REDACTED_WORKSPACE_CONFIG` is still what `Read pnpm workspace configuration` reads for the workspace globs.
- `REDACTED_LOCKFILE` — an approved copy of a discovered _text_ lockfile from which no version reached the output, in turn. Three ways that happens: the format has no adapter, which is `yarn.lock` and `bun.lock`; the file's own row refused it, so nothing was read; or the row read it and emitted no version, which is what a `pnpm-lock.yaml` outside the closed set of lockfile versions returns — `uncertain` with every version field rejected, not `refused`. The test is the output rather than the format, because those last two leave a file whose row exists and whose versions are still missing. A `package-lock.json`, `npm-shrinkwrap.json` or `pnpm-lock.yaml` that did emit its versions needs no copy. This bullet is where that division is stated, and the paragraphs below cite it rather than restating it. Never `bun.lockb`: ripgrep stops at its first NUL byte and exits 0 having printed nothing, which is indistinguishable from a lockfile that holds no entry for these packages.
- `NATIVE_ROOT` — each platform's native root in turn, resolved per platform: the `sourceDir` that `react-native.config.js` declares for it, or `"$APP_DIR/ios"` / `"$APP_DIR/android"` for a platform it does not mention. A declared `sourceDir` is relative to the app root, so `NATIVE_ROOT="$APP_DIR/<declared sourceDir>"` unless the declared path is already absolute. Assign it before every row that reads it; git rejects an empty pathspec outright.
- `REDACTED_NATIVE_INPUT`, `REDACTED_CI_CONFIG`, `REDACTED_WORKSPACE_CONFIG`, `REDACTED_MANIFEST`, `REDACTED_EAS_CONFIG` — an approved copy of each discovered file, before any row prints what it contains. A row that has no copy does not run, and the input is reported as unread.
- Every `rg` row passes `--no-config` so a caller's `RIPGREP_CONFIG_PATH` cannot add globs or options to the input set this table defines.
- `IGNORE_PATH` — each path whose ignore rule is being read: a native root, and then each file the root's scan returned.

`Find app-level configuration` stops at the app root's own directory, and everything deeper is reached through a native root instead. A recursive scan of the app root returns a vendored or fixture `Podfile` as readily as the real one, and the assessment has no way to tell them apart afterwards.

Only the two rows that read a native surface pass `--no-ignore`, because only they search inside directories a project ignores wholesale: an ignored directory is pruned before an include glob can match anything under it, while an ignored _file_ is still returned by an explicit `-g` include.
`--no-ignore` rather than `--no-ignore-vcs`, because the latter disables only source-control ignore files and leaves `.ignore` and `.rgignore` in force; a project that lists a generated `ios/` in either would otherwise vanish from the scan.
`Scan a native root` therefore carries its own excludes for build output, which `.gitignore` would otherwise have pruned; `Find app-level configuration` needs none, because `--max-depth 1` cannot reach into a build directory.

`Read an external Node pin` takes the original for all five names, and each one is read by the adapter its format has rather than printed. What reaches the output is one validated version, so `mise.toml`'s `[env]` table and another tool's line in a `.tool-versions` have no field to leave through and nothing has to separate them.
That is the second answer this file has given for that table. The first was a redacted copy, which worked because a copy has nothing to hide; before it, an earlier form tried to separate the pin from `[env]` by pattern and could not — a key-only pattern printed `node_auth_token`, and a `[tools]`-section range missed `[tools.node]`, a dotted `tools.node` key and a header with a trailing comment. Bounding the output rather than the input is what removed the question in both directions.

`Read Yarn configuration keys` reads named keys rather than the whole file, because a `.yarnrc.yml` can hold `npmAuthToken`. Each pattern anchors to the whole key and its colon, quoted or not: a prefix match would print a custom key such as `nodeLinkerAuthToken` along with its value and the explicit glob returns it even where the project ignores the file. Use it for `.yarnrc.yml`; `Read pnpm workspace configuration` reads `pnpm-workspace.yaml` whole. Both read a redacted copy, so neither restriction is what makes them safe — the named keys are what the assessment needs, and nothing more.
`Read a Yarn linker` reads the same file as the first of those, on the original, for the one key in it that has a closed set of values. Two rows over one file is the shape `eas.json` already has: this one adds the linker as typed evidence, and the copy row still supplies `yarnPath`, `nmHoistingLimits`, `pnpMode` and `enableScripts`, which no schema names.
What that buys is not a shorter key list. A key list is what the copy row needs because it prints lines; the typed row prints a value its type accepted, so `npmAuthToken` has no field and no path out whatever a project calls it.
`Read a pnpm lockfile` takes the original for the two things a `pnpm-lock.yaml` holds that have a type: the version that wrote it, which is a member of a closed set, and the version the selected importer resolved for `react`, `react-native` and `expo`, which is an exact version. Everything else in the file is left unaddressed, the credentialed `tarball` and `specifier` entries with it, so this row needs no copy and no key list.
It replaces the extraction row's reading of that file rather than adding beside it, and the `REDACTED_LOCKFILE` bullet above is where that division is stated. What it removes is a pattern over a lockfile, which is the operation this architecture exists without.

`Read a pnpm workspace catalog` reads the same file as the second of those, on the original, for the one thing in it that has a type: a catalog entry for `react`, `react-native` or `expo` is a dependency range, and a manifest that uses the catalog writes `catalog:` where the range would be. The copy row still supplies the workspace globs, which are project text with no shape a schema could bound.

`Report whether a native root exists` reports a third outcome, `outside-repository`, and no later row runs for such a root: a declared `sourceDir` can be absolute or climb out with `..`, and a `--no-ignore` scan rooted at `/` would walk the host filesystem. The row canonicalises both paths with `cd` and `pwd -P` before comparing, so a `..` segment and a symlink under the repository that points out of it are both caught; a textual prefix test misses each of them. A root that cannot be entered is reported `absent`, which is also the only case where nothing can be traversed. Report the native surface as `[UNCERTAIN]` and name the declared value.
`Report whether a native root exists` takes one root per run, so it runs once per platform with `NATIVE_ROOT` set to that platform's resolved root.
Run it before the tracking-state row.
Both git rows exit 128 when `$APP_DIR` is not inside a worktree, and when `$NATIVE_ROOT` resolves outside the one it is in; that is neither tracked nor untracked, so report native ownership as `[UNCERTAIN]` and say which of the two it was. `git ls-files --error-unmatch` exits 1 for a directory that does not exist and for one that exists untracked alike, so only the existence check separates them; a tracked directory exits 0 and lists its files.
`Read a path's ignore rule` returns the path it was given when that path is ignored, and nothing when it is not. It does not pass `-v`, which prints the ignore file, its line number and the matching pattern: that is a project file's content, and this row has no approved copy to read it from. The ownership assessment needs whether a path is ignored, not which rule did it.
It passes `--no-index` because git otherwise suppresses a match for any path already in the index, and a generated native root holding a force-added file is exactly the case the ownership assessment needs to see.
Run it for the root and for the paths the root's scan returned: a rule such as `ios/*` or `*.xcodeproj` leaves the root itself unmatched while ignoring its contents, so the root alone does not carry the evidence.

A local reference that `Find local CI references` turns up needs a redacted copy of its own before it can be read: assign that copy to `REDACTED_CI_CONFIG` and run `Inspect CI Node and verification inputs` again; that row is how a referenced file gets read, and no separate row exists for it.
A GitHub Actions reference often names a directory rather than a file (`uses: ./.github/actions/setup`); assign that directory's `action.yml`, or `action.yaml` when that is what exists, and report the reference as unresolved when neither does.

`Find CI configuration` tests the fixed locations each provider actually reads rather than globbing for them, so a workflow file inside an example app or a test fixture is not returned as this repository's CI. A nested configuration is read only when `Find local CI references` turns it up from an active one.

`Find generation and build declarations` takes a redacted copy of the app manifest, of `eas.json` when discovery returned it, and of each discovered CI configuration in turn.
It skips a variable that discovery left unset, so a project without `eas.json` or without CI still runs it.
It is not limited to GitHub Actions, because the CI discovery row covers six systems.
